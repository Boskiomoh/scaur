# Scaur architecture

How the Scaur storefront is built. Read with [`PRD.md`](PRD.md) (behaviour) and [`DESIGN-SPEC.md`](DESIGN-SPEC.md) (looks). The artboards in [`design/`](design/) are the visual reference; `design/Kit.dc.html` also holds the reference implementation of the kit rules in section 5.

## 1. Principles

1. **Shopify is the source of truth** for products, prices, stock, images and the cart. The app never stores commerce data of its own.
2. **Server first.** Pages are Server Components that fetch from the Storefront API with a server-only private token. Client components are small leaves: switches, pickers, the cart drawer, the kit builder's controls.
3. **State lives in the URL** wherever a person might want to share or go back to it: filters, variant choice, the whole kit.
4. **Pure logic is separate and tested:** `src/lib/kit.ts`, `src/lib/catalog.ts` (tag parsing), `src/lib/format.ts` have no React or network code.
5. **Zero running cost:** Vercel Hobby, a Shopify development store, no paid apps or APIs.

## 2. Stack

- Next.js 16 (App Router, Server Components, Server Actions), React 19, TypeScript strict.
- Tailwind CSS v4 (`@theme` tokens in `src/app/globals.css`).
- React Compiler (`reactCompiler: true`, `babel-plugin-react-compiler`), per the house style.
- Zod for parsing Storefront responses and URL params.
- `@phosphor-icons/react` (regular weight) for icons.
- Dev only: `sharp` (thermal images, favicons), `vitest`, `@playwright/test`, `@axe-core/playwright`, `prettier`.
- Proposed, needs approval: `zustand` for the cart store (house style section 4: state shared by distant components: the header badge, add buttons and the drawer).

No Shopify SDK is required: the Storefront API is one GraphQL endpoint and a typed `fetch` wrapper is smaller than any client library. No state library: the cart lives on Shopify, and UI state is local or in the URL.

This Next.js version has breaking changes from older training data. Before writing framework code, read the relevant guide in `node_modules/next/dist/docs/` (caching, `searchParams`, Server Actions, `proxy.ts`).

component each, thin routes that render one feature component, and each feature's parts,

covers all its users; shared by two features means `components/ui`, `hooks`, `lib` or `types`.

**Code style** (the skill's sections 2 to 11): `const Name: FC<NameProps> = (...) => {}` with
`export default Name` at the bottom and props as an `interface`; framework files use
`export default async function Page()`. Server components by default; `"use client"` only on
the smallest leaf. React Compiler on, so no `useMemo`, `useCallback` or `React.memo`.
`useEffect` only to sync with something outside React. Tokens only in classes (no raw hex,
no arbitrary values), logical spacing utilities, Phosphor icons imported per icon with
`aria-hidden` when decorative. Prettier defaults (double quotes, semicolons, trailing commas).
Only the section labels (`// State`, `// Derived`, `// Handlers`...) and one-line *why*
comments. No `any`, no enums, types derived from Zod schemas.

## 4. Shopify data layer

**Endpoint:** `https://${SHOPIFY_STORE_DOMAIN}/api/${SHOPIFY_STOREFRONT_API_VERSION}/graphql.json`, POST, header `Shopify-Storefront-Private-Token: ${SHOPIFY_STOREFRONT_PRIVATE_TOKEN}`. Version `2026-07`. The client is `server-only`.

```ts
// lib/shopify/client.ts
export async function storefrontFetch<T>(
  query: string,
  variables: Record<string, unknown> = {},
  opts: { tags?: string[]; revalidate?: number | false; cache?: RequestCache } = {},
): Promise<T>
// Throws ShopifyError { kind: 'network' | 'graphql' | 'userErrors', messages }.
```

**How the layering system is stored in Shopify** (no metafield setup needed):
- **Layer** = product type: `Base`, `Mid`, `Insulation`, `Shell`.
- **Range, warmth and role** = tags: `temp-lo:25`, `temp-hi:60`, `warmth:2`, `shell-role:storm|rain|showers|wind`, plus `demo`.
- **Colour and Size** = product options, in that order. Variant images carry the colourway photo.

`lib/catalog.ts` maps a raw product to:

```ts
type Layer = 'base' | 'mid' | 'insulation' | 'shell';
type Product = {
  handle: string; title: string; descriptionHtml: string;
  layer: Layer; range: { lo: number; hi: number }; warmth: number; shellRole?: 'storm' | 'rain' | 'showers' | 'wind';
  price: { amount: string; currencyCode: 'USD' };
  colours: { name: string; hex: string; image: Image; variants: Variant[] }[];   // hex from a small map in lib/catalog.ts
  images: Image[];
};
type Variant = { id: string; colour: string; size: Size; availableForSale: boolean; quantityAvailable: number | null; price: Money };
```

A product with missing or malformed tags is logged and excluded from the axis, kit and range bars rather than crashing a page. Unit tests cover the parser.

**Queries:** `products(first: 50)` (the whole catalog is 11 products; fetch once, filter on the server), `product(handle)`, `predictiveSearch(query, types: PRODUCT)`, `cart(id)`, and mutations `cartCreate`, `cartLinesAdd`, `cartLinesUpdate`, `cartLinesRemove`. Request `quantityAvailable` on variants (the Headless channel must have "Read product inventory" access; see WORKFLOW step B).

## 5. The kit rules (`lib/kit.ts`)

Pure function; `design/Kit.dc.html` is the reference and must stay identical.

```ts
type KitInput = {
  activity: 'run' | 'hike' | 'alpine';
  temp: number;                 // °F, -10 to 70
  rain: 'dry' | 'showers' | 'steady';
  wind: 'calm' | 'breezy' | 'gusty';
  size: Size;
  pick?: Partial<Record<Layer, number>>;   // swaps: index into that layer's list
  off?: Partial<Record<Layer, boolean>>;   // removed by the shopper
  on?: Partial<Record<Layer, boolean>>;    // added back by the shopper
};
```

1. `output = { run: 12, hike: 0, alpine: -10 }[activity]`
2. `feels = temp + output - { calm: 0, breezy: 6, gusty: 14 }[wind] - (rain === 'steady' ? 6 : 0)`
3. Needed layers: base always; mid if `feels < 58`; insulation if `feels < 30`; shell if `rain !== 'dry' || wind === 'gusty' || feels < 20`. A layer is in the kit when `(needed && !off) || on`.
4. Layer lists (swap order): base `[tarn-merino-crew, tarn-merino-quarter-zip]`; mid `[knoll-quarter-zip, knoll-grid-fleece, bothy-pile-jacket]`; insulation `[belay-hoody, cornice-down-jacket]`; shell `[squall-jacket, ridgeback-softshell, downpour-jacket, scarp-shell]`. In the app these lists are built from Shopify products of that layer, ordered by warmth then price, which gives exactly these orders for the seed catalog.
5. Automatic picks:
   - base: `feels < 45` ? quarter-zip : crew
   - mid: `feels < 22` ? bothy : `feels < 42` ? knoll-grid : knoll-quarter-zip
   - insulation: `feels < 8` ? cornice : belay
   - shell: steady rain ? (`feels < 32` ? scarp : downpour) : showers ? squall : `feels < 20` ? scarp : ridgeback

   Picks resolve by position in the ordered list for base, mid and insulation (0 = first), and by the `shell-role` tag for shells (storm = scarp, rain = downpour, showers = squall, wind = ridgeback), so renaming a product in Shopify doesn't break the rules.
6. `warmth = sum(item.warmth) + (shell in kit && wind !== 'calm' ? 1 : 0)`
7. `floor = 70 - warmth * 6 - output` ("comfortable down to", °F)
8. `ok = floor <= feels - output` (the kit covers the start conditions); summary sentence per PRD F10.
9. Thermal figure level: `clamp(pieces - 1 + (warmth >= 9 ? 1 : 0), 0, 4)`.
10. Size availability: if the picked product has no available variant in `size` (any colour), take the next product in that layer's list that has one; if none, the slot reports "Sold out in <size>".
11. Empty-slot reasons: mid "Warm enough to skip a mid layer at T°F"; insulation "No insulation needed at T°F"; shell "Dry and not too windy: no shell needed".

Worked example (the default state): hike, 38°F, steady rain, breezy, M. `feels = 38 + 0 - 6 - 6 = 26`. Kit: Tarn Merino Quarter-Zip, Knoll Grid Fleece, Belay Hoody, Scarp Shell. `warmth = 2 + 2 + 4 + 1 + 1 = 10`, `floor = 10°F`, `ok = 10 <= 26`, figure level 4, total $782.

**URL:** `/kit?a=hike&t=38&r=steady&w=breezy&s=M&pick=mid.2&off=insulation&on=` (compact, parsed and validated by `lib/url.ts`; invalid values fall back to defaults).

## 6. Cart

- `src/components/cart/actions.ts` ("use server") exposes `addLine(variantId, qty)`, `addKit(lines, kit)`, `updateLine(lineId, qty)`, `removeLine(lineId)`, `getCart()`.
- The cart id lives in an httpOnly, secure, sameSite=lax cookie `scaur_cart` (30 days). The first add calls `cartCreate`.
- Every action re-validates on the server before calling Shopify: variant exists, `availableForSale`, quantity at most `quantityAvailable`. The UI caps quantities too, but the server is the guard.
- `addKit` sends all lines in one `cartLinesAdd`, each with attributes `_kitId` (short random id) and `_kit` (label, for example "Day hike, 38°F, steady rain"). Attributes starting with `_` are hidden from the buyer at checkout. A third attribute, `_kitUrl`, stores the kit builder URL that produced the kit. The drawer groups lines by `_kitId`, and "Edit kit" links to `_kitUrl`.
- `src/store/cart-store.ts` (Zustand, one selector per value) holds the drawer's open state and the last cart from the server; components apply optimistic updates, and each action's returned cart replaces the stored one. A failed action restores the previous cart and puts the error on that line. The layout reads the cart on the server and seeds the store once.
- Checkout: the notice (PRD F9), then `window.location.assign(cart.checkoutUrl)`.

## 7. Thermal images

`scripts/thermal.mjs` (sharp) runs in `prebuild` and writes `public/thermal/<photo>.webp` for every photo in `assets/photos/` except the fabric close-ups, plus `public/thermal/kit-0.webp` to `kit-4.webp` from `shell-fog-ridge.jpg`. It is the same algorithm used for the design canvas:

1. Greyscale, then invert (dark fabric reads warm, bright sky reads cold).
2. Gaussian blur, radius 3 at 1200px wide (thermal sensors are soft).
3. Normalise, clipping 2% at each end.
4. For the kit levels only: `v' = clamp(v * slope + bias * 255)` with (slope, bias) = (0.55, 0), (0.65, 0.08), (0.72, 0.16), (0.78, 0.24), (0.80, 0.32).
5. Map through a 256-entry lookup table interpolated from the ironbow stops: 0.00 #140c2e, 0.22 #4a1a78, 0.45 #a3206f, 0.66 #e0452b, 0.84 #f79a2e, 1.00 #ffe08a (`lib/heat.ts` exports the same stops).
6. Resize to 1200px wide, WebP quality 78.

`lib/thermal.ts` maps `handle + colour` to a thermal file using `content/catalog.json` (each colour's `photo` key). Products without a match hide the switch. Thermal images are served locally (not from Shopify) because they are presentation, not product data.

## 8. Filters and URL state

- `/shop` reads `searchParams` (`layer`, `t`, `view`), validates with Zod, fetches the catalog once (cached, section 9) and filters on the server: layer by product type; `t` keeps products whose range contains it. Results render as Server Components; the filter bar is a small client component that updates the URL with `router.replace` (no scroll jump) and uses `useTransition` to show a pending state on the grid.
- `/products/[handle]` reads `colour` and `size`; the picker updates the URL with `replace`, so the back button leaves the page rather than stepping through choices.

## 9. Caching and freshness

- Catalog and product queries: cached with tags `products` and `product:<handle>`, revalidated every 5 minutes.
- Cart queries: never cached (`cache: 'no-store'`).
- Optional instant updates: `src/app/api/revalidate/route.ts` accepts Shopify's `products/update` webhook, verifies the HMAC with `SHOPIFY_WEBHOOK_SECRET`, and calls `revalidateTag`. Without it, changes show within 5 minutes.
- Use the caching API this Next.js version documents (`node_modules/next/dist/docs/`); do not copy patterns from older versions.

## 10. Images

- Product images: `next/image` with `remotePatterns` for `cdn.shopify.com`, explicit `sizes`, the hero and the product stage `priority`. Shopify's CDN resizes on request (`width` in the URL); use `next/image` with a custom loader for Shopify URLs so Vercel's image optimiser quota isn't spent.
- Thermal images: local WebP from `public/thermal/`.

## 11. SEO

- Per-route `generateMetadata`; product JSON-LD (`Product` with `offers`: price, currency, availability per variant).
- `robots: { index: false, follow: false }` in the root layout; `robots.txt` disallows all; the sitemap is still generated for completeness.

The store password is deliberately public: it only unlocks a private development store's storefront for testers and protects nothing else. Never put an Admin API token in this app.

**E2E (Playwright, against a production build and the real dev store)**
1. Home: the thermal switch swaps the image and `aria-pressed`, no layout shift.
2. Shop: filters update the URL; reload and back restore them; the empty state appears at 80°F.
3. Product: a sold-out size can't be selected; changing colour clears an unavailable size; add to cart opens the drawer with the right line.
4. Cart: quantity stops at stock; remove; the empty state; persists across reload.
5. Kit: the default kit matches the worked example; swap and remove update the total; "Add kit to cart" adds 4 grouped lines.
6. Checkout notice appears before leaving the site, and "Continue" points at a `checkout` URL on the store domain.
7. Keyboard only: open the drawer, change quantity, close with Esc, focus returns.
8. axe: home, shop, product, kit, and the open drawer have no violations.
9. Mobile 390px: menu sheet traps focus; no horizontal scroll.
